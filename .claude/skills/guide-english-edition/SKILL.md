# guide-english-edition

日本語の手順書（Markdown）から英語版を作る。**決定論で処理できる部分は必ず `scripts/` のプログラムに任せ、AI は翻訳と判断に専念する。**

**やること:** `doc/<ディレクトリ>/<名前>_en.md` の作成（原文と同じディレクトリ。`media/` は共有）、検証、PDF の点検。
**やらないこと:** 原文の変更。PDF の自動生成（PDF は VS Code 等でユーザーが生成する。`.gitignore` 済み）。コミット・プッシュ（ユーザーの指示があるときだけ）。

対象は `doc/drone-dev-env-setup-guide/` の `drone-dev-env-setup-guide.md`（CRLF）、`cc-…`（CRLF）、`blueos-…`（LF）、`wsl-docker-…`（LF）など。対象が曖昧なら、先にユーザーに聞く。

```bash
SKILL=.claude/skills/guide-english-edition/scripts
```

---

## フェーズ0: 準備

1. `git status` と `pwd` で状態を確認する。原文に未コミットの変更があれば、英訳の前にユーザーへ伝える（原文が確定してから訳す）。
2. 原文を通読し、版数・見出し構成・画像・表・コードブロックを把握する。
3. 表紙の組織名（`ドローンエンジニア養成塾 デベロッパーコース`）の公式な英語名は未定。既存の英語版で使われていなければ、**ユーザーに確認する**（勝手に決めない）。

## フェーズ1: 翻訳 — AI の仕事

`<名前>_en.md` を書く。大きいファイルは分割して追記する。

**構造は原文と同一に保つ**（検証で機械的に照合される）:
- 見出しの数・階層・番号（`2.3.1.` など）、`<div style="page-break-before:always"></div>` の位置、表の行数、コードブロックの数と順序、画像の数と順序。
- 表紙の `Ver.x.y.z - 日付` は原文と同じ。HTML コメントの改訂履歴・「変更履歴」表も訳す。

**訳さない:** コマンド、コード（コードブロック内の日本語コメントとプレースホルダは訳す）、URL、ファイル名・パス、製品名（ArduPilot、Mission Planner、BlueOS、MAVLink、WSL、Ubuntu 等）。プレースホルダの括弧 `＜ ＞`（全角）はそのまま使い、中身だけ英語にする（例: `＜あなたのGitHubアカウント名＞` → `＜your-GitHub-account-name＞`）。

**UI ラベル:** 実ソフトの**英語 UI の表記**に合わせる（例: Visual Studio Code の `File` → `Preferences`、Windows の設定画面）。自信のない用語は推測で書かず、フェーズ4の「要確認リスト」に入れる。

**画像:**
- 画像参照は原文と同じファイルを使う（`media/` を共有）。日本語 UI のスクリーンショットは差し替えられないので、フェーズ4で章ごとに列挙する。
- 図（SVG から書き出した PNG。例: `intro-010.png`）は、元の SVG の英語版（`droneschool-material` の `marp-english-edition` が作る `*_en.svg`）があれば、同じ手順で書き出して `media/<名前>_en.png` を作り、参照を差し替える。なければ原文のまま使い、報告する。

**訳語の目安**（既存の訳に揃える）:

| 日本語 | 英語 |
|---|---|
| 手順書 | setup guide |
| 機体 | vehicle |
| シミュレータ | simulator |
| アーム／離陸 | arm / take off |
| フォーク／クローン | fork / clone |
| ワークブランチ | working branch |
| 課題提出 | assignment submission |
| 期番号（`＜term_no＞`） | term number（例: `1st`, `2nd`） |
| 接続確認 | verifying the connection |

## フェーズ2: 機械処理と検証 — スクリプト

```bash
G=$SKILL/guide_check.py
D=doc/drone-dev-env-setup-guide
python3 $G eol-match $D/<名前>.md $D/<名前>_en.md    # 改行コードを原文に揃える
python3 $G toc-write $D/<名前>_en.md                  # 目次を英語の見出しから作り直す
python3 $G compare   $D/<名前>.md $D/<名前>_en.md     # 原文と照合
```

- `[NG]` をすべて解消するまで繰り返す。よくある原因: 見出し番号の欠落、改ページ `<div>` の取りこぼし、表の行の欠落、コマンドの改変、画像参照の誤り、全角記号の残り。
- `[WARN]`（コメント・コードブロック内の日本語の残り）は、意図した残りか確認する。改訂履歴のコメントは訳す。
- `[INFO]`（差し替えた画像・URL）は、意図したものか確認する。ドキュメントリンクは英語版があれば英語版 URL にする（例: `/ja/` → `/en/`）。
- 目次は手で直さない（`toc-write` が見出しからアンカーまで再生成する。最初の `#` 見出しより前の見出し（変更履歴）は目次に載せない、この手順書の慣習に従う）。
- `toc-check <ファイル>` は目次の整合だけを確認する（原文にも使える）。

## フェーズ3: PDF の点検 — ユーザーの再生成後

1. ユーザーに、`_en.md` から PDF を生成してもらう（VS Code の Markdown PDF 等。自動生成はしない）。
2. 点検する。

```bash
python3 $SKILL/pdf_pages.py <名前>_en.pdf --ref <名前>.pdf --md $D/<名前>_en.md --render /tmp/en-pages
```

3. `[NG]`（PDF が `.md` より古い）は再生成を依頼する。`[WARN]` のページ（本文がほとんどない、見出しが末尾に取り残された）は、描画された PNG で見て判断する。
4. **図・表・コードのあるページを中心に目視**する。英語は日本語より横に長くなるので、表・図の箱・コードのはみ出し、画像だけのページ、目次の次ページへのはみ出しを見る。
5. 対処は原文を触らずに、訳文の短縮・画像幅の調整・改ページ位置の調整で行う（改ページを動かした場合は原文との位置照合に影響するので、`compare` を再実行して差を把握する）。

## フェーズ4: 報告

- 作成したファイル（`_en.md`、`_en.png` など）と、PDF のページ数（原文との差）を報告する。
- **要確認リスト**（自信のない UI 用語、組織名など）と、**未対応の画像**（日本語 UI のスクリーンショット、英語版のない図）を章ごとに示す。
- コミット・プッシュはユーザーの指示があってから行う。
